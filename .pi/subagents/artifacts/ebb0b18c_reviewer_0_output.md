## Review

**Correct — what is sound:**
- The Python-core + TS-shell split is a legitimate v0.1 pattern: one algorithm implementation reused by CLI, Claude hook, and pi extension; per-process isolation means a crash or timeout never corrupts the agent loop. The fail-open discipline (`never throws`, short timeouts, `{}` on failure) is consistently applied across all three surfaces (`index.ts:55-58`, `before_prompt.py:69-100`, `runCli` in `cli.ts:118-143`).
- The dedup guard actually works: `index.ts:45` checks for `"CKG Structure Map"`, which *is* present in `ckg inject` output via `STRUCTURE_MAP_TEMPLATE` (`claude/prompts.py:31`), so no unbounded systemPrompt growth.
- PGQ fallback semantics for *load* are correct: `cmd_load` fails hard when Oracle is unreachable (persistence must not silently no-op), while query/inject degrade to memory.
- Packaging is defensible: `files` whitelist + `.npmignore` double-cover Python artifacts, postinstall is non-fatal (never breaks `npm install`), CI runs real tests + CLI smoke, and the `pi-package` keyword + README-as-landing-page satisfy the pi.dev listing shape.

**Findings (severity, rationale, alternative):**

- **WATCH — Pool lifecycle: `connect_pgq` creates pools and never closes them** (`storage/connection.py:83-90`). `cmd_query`/`cmd_inject`/`cmd_load` leak a pool per call; only `oracle_summary` closes (line 145-147). The leak is masked because every consumer (pi extension, hook, CLI) spawns a fresh Python process per call, but any long-lived embedding of `ckg` as a library accumulates connections. Alternative: return pools via a context manager (`with connect_pgq() as mem`) or `finally: pool.close()` in the three `cmd_*` functions; also set `connect_timeout` in `create_pool` (unreachable DSNs currently hang well past the pi/hook kill deadlines).
- **WATCH — PGQ mode reporting is misleading** (`retrieval/hybrid.py:90-117`). Two traps: (a) `connect_pgq` failure yields `method="memory"` with no actionable hint — the "actionable PGQ fallback message" from 1571bd6 only covers the *query-time* exception path (hybrid.py:107-111); (b) with `CKG_ORACLE_DSN` set but the graph never `ckg load`-ed (e.g., DSN configured for a different project), anchors don't exist in PGQ, `match_neighborhood` returns empty, and the method string still reports `"pgq"` while effectively doing anchor-only in-memory PPR. Alternative: check anchor presence in the DB and report the actual mode (`pgq: anchors-missing, graph not loaded`).
- **WATCH — Per-prompt subprocess + cold start is the scaling ceiling** (the #1 architecture question). Every coding prompt pays Python interpreter + numpy import + full `code_graph.json` re-read + fresh Oracle pool. Fine for small repos within the 12s budget; degrades on large graphs, and there is no observable signal when the 12s/8s deadline silently kills injection. The better distribution pattern is a `ckg serve` daemon (stdin JSON-RPC or a Unix socket) holding the parsed graph and a warm pool, with the current one-shot as fallback — plus a sidecar pickle cache of the parsed graph alongside the JSON.
- **WATCH — `before_agent_start` injection is query-frozen** (`index.ts:44-47`). The guard prevents growth but also means the map (which embeds `**Query**: <first prompt>`) is fixed at the first coding prompt; if this event fires per-turn, later different tasks get a stale map, and concurrent agent starts can race (both read pre-map systemPrompt, both append — last write wins). The Claude hook (per-prompt `additionalContext`) has better fidelity. Alternative: use a per-turn prompt-stage event with replace semantics if pi exposes one; otherwise key the guard on a per-turn marker and re-inject with the current prompt.
- **WATCH — Background build quality and recovery** (`context.ts:80-91`). (a) `--pkg-root` defaults to the directory name — wrong for `src/`-layout repos and monorepos, silently degrading import-edge resolution (and thus retrieval). (b) A build killed by the 120s timeout mid-`write_text` can leave a truncated `code_graph.json`; `hasGraphCache` then reports present forever, injects silently fail, and `buildsStarted` prevents retry — no recovery path. (c) No lockfile; a session restart during an in-flight build can start a second concurrent build. Alternative: derive `pkg_root` from `pyproject.toml` (setuptools package-dir / `src/` listing), write atomically (tmp + rename), and add a build lockfile.
- **WATCH — Claude Code marketplace path has no Python bootstrap** (`.claude-plugin/plugin.json`, `hooks/before_prompt.py:46-58`). `claude plugin marketplace add jasperan/ckg && claude plugin install ckg` clones from GitHub with no npm postinstall → no `.venv` → `find_ckg` falls to PATH `ckg`, which most users won't have → hook emits `{}` and the plugin silently does nothing. The README's Claude install section is the only path that never installs the Python core. Alternative: have the hook run a one-time bootstrap (`uv sync`) or emit a visible warning once instead of silent `{}`; document `pip install ckg` as a prerequisite in the Claude section.
- **WATCH — Declared-but-unused heavy deps contradict "Oracle is optional"** (`pyproject.toml:20-33`). `oracleagentmemory`, `langchain-oracledb`, `langgraph-oracledb` are imported nowhere in `src/` (verified by grep — only `oracledb` is used) yet are mandatory `dependencies` and duplicated in the `oracle` extra. Every in-memory-only user installs the full Oracle/langchain stack. Alternative: keep base deps to `numpy`, `pyyaml`, `oracledb`; move the rest to the `oracle` extra (imports are already lazy).
- **WATCH — PGQ staleness: upserts never delete** (`oracle_pgq.py:145-192`). Re-runs of `ckg load` after a rebuild accumulate stale nodes/edges (MERGE only inserts/updates; `create_property_graph` drops/recreates the graph but not the tables), so `oracle-status` node/edge counts drift upward forever. Retrieval self-heals (neighbors are filtered to local nodes in `hybrid.py:97-101`) but the store and status lie. Alternative: delete the domain's rows before upsert, or add a `build_id` column filtered in matches.
- **WATCH — `match_neighborhood` runs one GRAPH_TABLE query per hop** (`oracle_pgq.py:87-126`) — 2 hops × 5 anchors = 10 round-trips per prompt, despite the README advertising quantified paths. Alternative: a single `MATCH (v)-[e]->{1,h}(w)` with `COLUMNS (w.id, MIN(length(e)))`.
- **WATCH — `pi -e` / dev-checkout discovery fallback is likely broken** (`cli.ts:73-83`). `uv run --no-project ckg` runs in an isolated env without installing the project, so `ckg` won't resolve in a fresh clone — the tier-3 fallback fails and the user gets "CKG CLI not found", contradicting the README's "try it for one session" claim. Alternative: `uv run --project <pkgRoot> ckg` (syncs from pyproject/uv.lock) or a lazy `uv sync` on first use.
- **WATCH — Windows support is inconsistent** (`cli.ts:66`, `before_prompt.py:46-58`). Discovery checks only `.venv/bin/ckg` (POSIX), while `postinstall.js` correctly creates `Scripts/ckg.exe` on win32; the hook hard-codes `python3`. Alternative: platform-aware venv path in `discoverCli` and `python`/`py -3` resolution in the hook.
- **WATCH — Default DB credentials in code** (`connection.py:41-42`). `dmuser`/`continual_learning` defaults match the docker quick-start, but anyone setting only `CKG_ORACLE_DSN` silently authenticates with a well-known password against whatever DSN they configured. Alternative: require USER+PASSWORD when DSN is set, with an explicit error.
- **WATCH — Version/license metadata drift**: `0.1.0` is duplicated across `package.json`, `pyproject.toml`, `.claude-plugin/plugin.json`, `marketplace.json`, and two `SKILL.md` files; license is "MIT" in `package.json`, "MIT OR Apache-2.0" in `pyproject.toml`+classifiers, while `LICENSE` is MIT-only. Alternative: derive plugin/marketplace versions at release time from `pyproject.toml`; align the declared license with the LICENSE file.
- **WATCH — pi.dev catalog image 404**: `package.json` `pi.image` → `docs/ckg-banner.png`, but no `docs/` dir exists in the repo or the `files` whitelist. Alternative: add the asset or drop the field.
- **WATCH — Triplicated logic**: project detection exists three times (`pi/extensions/ckg/project.ts`, `claude/plugin.py:17-31`, `hooks/before_prompt.py:29-41`) and the injection preamble three times (`context.ts:33-40`, `before_prompt.py:17-26`, `claude/prompts.py:8-23`) — guaranteed drift over time. Alternative: a single `ckg detect`/`ckg preamble` CLI subcommand both shells share.
- **Note — loose peerDependencies** (`package.json:43-46`): `typebox: "*"` is a runtime import; `"*"` invites breakage. Pin a caret range matching pi's bundled version.
- **Note — `.ckg/` is written into user repos** (build output) with no global ignore story; users' projects will accumulate an untracked cache dir. Consider an `XDG_CACHE_HOME` default with project-local override.
- **Note — SQL identifiers interpolated from env into DDL/SQL** (`oracle_pgq.py` f-strings): user-controlled env only, but a `[A-Za-z0-9_]+` validation on `graph_name`/`table_prefix` is one line and removes the foot-gun.

**Line-level observations folded in (not the focus):** parser pass-2 call resolution passes an empty `sym_by_name` (`parser.py:184`) so the "prefer local name" branch is dead code, and caller node ids (`sym:<file>::<callee>`) often don't exist as nodes; PPR tolerates this, but call-graph accuracy underpins the recall claims — worth a correctness pass before quoting numbers for arbitrary repos.

**Architectural status: WATCH.** The split, the fail-open injection design, and the PGQ fallback strategy are sound for 0.1. The items that will bite users/maintainers soonest: the Claude marketplace path silently no-oping without a Python install, the misleading `"pgq"` method string, stale-PGQ drift, the src-layout `pkg_root` heuristic, and the lack of any warm-path for per-prompt retrieval. None are un-shippable; all are pre-1.0 debts. No BLOCK findings.
